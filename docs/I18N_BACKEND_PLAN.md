# Termojet — план перекладу контенту з БД (бекенд i18n)

Статус фронтенду: UI/chrome + код-контент (homeContent/aboutContent/categories) **вже перекладені**
(5 мов, задеплоєно). Лишився **контент із БД** (SQLite, better-sqlite3) — він однаковий у всіх мовах.
Цей документ — план, як його перекласти.

## 1. Що саме треба перекласти (сутності та поля)

| Таблиця | Поля для перекладу | Не чіпати | Фронт уже готовий? |
|---|---|---|---|
| `products` (331 шт.) | `name`, `short_desc`, `description`, `specs` (ключі + текстові значення), `subcategory`, `features`, `seo_title`, `meta_description` | `sku`, `price`, `slug`, `images`, числові значення specs (130 мм, 1″) | ✅ `name_<lang>`, `desc_<lang>` читаються; ❌ specs/short/seo — ні |
| `blog_posts` | `title`, `excerpt`, `content`, `category`, `tags` | `slug`, `image`, `published_at` | ✅ `title/excerpt/content_<lang>` читаються; ❌ category/tags — ні |
| `portfolio` | `title`, `description`, `location`, `power` | `images`, `year` | ❌ ще не підключено |
| `reviews` | `text`, `company` | `name` (власне ім'я), `rating` | ❌ |
| `faqs` | `question`, `answer` | `sort` | ❌ |
| `settings` | `address`, `workHours` | `phone`, `email`, `telegram` | ❌ |
| `banners` / `promos` | текстові поля (якщо є) | посилання, зображення | ❌ |

**Обсяг:** ~20 тис. символів назв + ~1.2 млн символів описів товарів + блог/портфоліо. × 4 мови (EN/PL/FR/DE).
→ ручний переклад нереальний, потрібен **автоматичний LLM-пайплайн** + можливість ручної правки в адмінці.

## 2. Архітектура зберігання — рекомендація

**Варіант, що рекомендую: один JSON-стовпець `i18n` на кожну таблицю.**

```sql
ALTER TABLE products ADD COLUMN i18n TEXT DEFAULT '{}';   -- ідемпотентно, як решта міграцій
-- i18n = { "en": {"name":"...","description":"...","specs":{...}}, "pl": {...}, "fr": {...}, "de": {...} }
```

Чому так (а не окремі колонки `name_en, name_pl…`):
- Один міграційний крок на таблицю; **додати нову мову = без зміни схеми**.
- UA лишається канонічним у наявних полях (`name`, `description`, `specs`) — нічого не ламаємо.
- API на віддачі **розкладає** `i18n[lang]` у пласкі поля `name_<lang>`, `desc_<lang>` тощо — рівно те, що **фронтенд уже очікує** (`p[`name_${lang}`]`). Нуль змін у вже-підключених місцях.

Альтернатива (окрема таблиця `translations(entity, id, lang, field, value)`) — гнучкіша для дуже багатьох
мов, але зайвий JOIN і складніша віддача. Для 4 фіксованих мов JSON-стовпець простіший.

## 3. Пайплайн авто-перекладу (одноразовий + інкрементальний)

Скрипт `backend/scripts/translate-content.mjs`:
1. Іде по рядках кожної таблиці, для кожної мови EN/PL/FR/DE.
2. Бере UA-джерело (name/desc/specs…), рахує його хеш; якщо `i18n[lang]._srcHash` збігається — **пропускає**
   (ідемпотентність, дешеві повторні прогони після правок).
3. Викликає **Claude API** (рекомендую `claude-haiku-4-5` — дешевий, якісний для перекладу;
   складні юридичні/маркетингові — можна `claude-sonnet-4-6`). Промпт: «технічний переклад
   опалювального обладнання, зберегти бренди/одиниці/HTML-теги, не перекладати SKU/числа».
4. Записує `i18n[lang]` + `_srcHash`. Батчами (наприклад, по 20 товарів за виклик через structured output),
   з рейт-лімітом і резюмуванням.

**Specs окремо:** перекладати лише **ключі** (мітки: «Підключення до колектора») і **текстові значення**
(«З термокраном»); числові/одиниці («130 мм», «1″») лишати як є (детект регуляркою).

**Оцінка вартості (одноразово):** ~1.2 млн UA-символів описів ≈ ~0.8 млн вх. токенів; ×4 мови
із Haiku (~$1/$5 за М ток.) ≈ орієнтовно **$15–40** разово. Інкрементально (нові/змінені товари) — копійки.
Час: кілька годин роботи скрипта з рейт-лімітом.

## 4. Найскладніше: specs + фільтри каталогу

Значення specs (і мітки фільтрів типу «З термокраном», «Без ізоляції») **водночас показуються і
використовуються як ключі зіставлення** у фільтрації (CatalogPage). Якщо просто перекласти — зламається фільтр.

**Рішення (той самий патерн, що вже застосовано для FilesPage/категорій):**
- UA-значення specs лишається **канонічним ключем зіставлення** (фільтр працює як раніше).
- Переклад specs живе в `i18n[lang].specs` лише для **відображення**.
- CatalogPage/ProductDetail рендерять `i18n[lang].specs[key]` (мітку й значення), а фільтрують по канонічному UA.
- Потрібен рефактор CatalogPage: розчепити «текст для показу» і «значення для матчингу» (зараз злиті в `opt.label`).

## 5. Зміни в API (backend/routes/*.js)

- `parseProduct` (і аналоги в blog/portfolio/reviews/faq/settings): після читання рядка —
  `const i = JSON.parse(row.i18n||'{}')` і додати пласкі поля: `name_en, name_pl, …, desc_en, …,
  specs_en, …` зі `i`. Фронт це вже споживає для name/desc/blog.
- Альтернатива: приймати `?lang=` і віддавати вже локалізовані поля. Але пласкі `*_<lang>` ближчі до
  наявного фронту — рекомендую їх.
- На збереженні (admin PUT/POST): чистити `i18n` для змінених полів (щоб пайплайн перепереклав), або
  одразу викликати переклад (див. §7).

## 6. Зміни у фронтенді

Уже готово (читає `*_<lang>`): товари `name`/`desc`, блог `title`/`excerpt`/`content`.
Треба додати таке саме читання `(lang!=='uk' && x[`field_${lang}`]) ? … : x.field` для:
- products: `short_desc`, `specs` (відображення), `seo_title`/`meta_description`, `subcategory`;
- blog: `category`, `tags`; portfolio: `title`/`description`/`location`/`power`;
- reviews: `text`/`company`; faqs: `question`/`answer`; settings: `address`/`workHours`;
- CatalogPage фільтри: показ перекладеної мітки, матчинг по канонічному UA (§4).

## 7. Адмінка (опційно, але бажано)

- У редакторах товару/блогу/тощо додати вкладки мов (EN/PL/FR/DE) з полями перекладу.
- Кнопка **«Перекласти автоматично»** → дергає той самий пайплайн для одного запису (заповнює, далі редактор править).
- Хук «при збереженні UA-контенту → інвалідувати/перекласти i18n» — щоб переклади не застарівали.

## 8. План впровадження (поетапно, низький ризик)

1. **Міграція схеми** — `ALTER TABLE … ADD COLUMN i18n` для products/blog/portfolio/reviews/faqs (+ settings підхід). Безпечно, ідемпотентно.
2. **API-віддача** `*_<lang>` полів (без перекладів ще — фолбек на UA лишається). Деплой — нічого не змінюється візуально.
3. **Пайплайн перекладу** — прогнати на products (найбільший обсяг) → перевірити кілька карток у EN/PL.
4. **Фронт-вирінг** решти сутностей (portfolio/reviews/faq/settings/specs-display).
5. **CatalogPage фільтри** — розчеплення показ/матчинг (найделікатніше, тестувати фільтрацію).
6. **Блог/портфоліо/відгуки/FAQ** — прогнати пайплайн, підключити.
7. **Адмінка** — вкладки мов + кнопка авто-перекладу.
8. Прогнати інкрементальний пайплайн, фінальний візуальний QA по всіх мовах.

## 9. Оцінка зусиль

| Етап | Орієнтовно |
|---|---|
| Схема + API-віддача `*_<lang>` | 0.5 дня |
| Пайплайн перекладу (скрипт + промпти + ідемпотентність) | 1 день |
| Прогін перекладу + перевірка (товари) | 0.5 дня (+ машинний час) |
| Фронт-вирінг решти сутностей | 1 день |
| CatalogPage фільтри (показ vs матчинг) | 0.5–1 день |
| Адмінка (вкладки + авто-переклад) | 1–1.5 дня |
| **Разом** | **~5 робочих днів** + ~$15–40 разовий API-кост |

## 10. Рішення, які треба ухвалити перед стартом

1. Зберігання: **JSON `i18n` стовпець** (рекомендую) чи окремі колонки `*_<lang>`?
2. Якість перекладу: повністю авто (Haiku) чи авто + ручна вичитка ключових (назви категорій, топ-товари)?
3. SEO: перекладати `seo_title`/`meta_description` + плюс локалізовані URL/слаги? (впливає на sitemap/redirects).
4. Адмінка: робимо вкладки перекладу зараз чи лишаємо авто-пайплайн і ручну правку пізніше?
5. Контакти/адреси: перекладати адресу/години (тут «Пн-Пт» → «Mon-Fri») чи лишити?
